# Client feedback traceability

The client requests below were relayed by Ms. Vera and are paraphrased as operational use cases. Status is based on the current code, models, tests, and available model assets; advanced requests are not represented as completed work.

| Requested use case | Current status | Current implementation/evidence | Current limitation | Planned future deployment | Demo wording |
|---|---|---|---|---|---|
| Unattended item detection | Implemented in current PoC | MonitoringZone thresholds/classes, YOLO or SecurePi people/object proximity, elapsed unattended timer, DetectionAlert, linked IncidentLog, cooldown and lifecycle updates. | Depends on supported object classes, camera geometry, thresholds, and PoC tracking; not a safety-certified detector. | Calibrate per zone with representative footage and operational acceptance tests. | "The PoC detects supported objects left without a nearby person for the configured time and creates a linked alert and incident." |
| Forgotten belongings at tables/seats | Partially supported | The unattended-object rule can flag supported belongings without a nearby person. | It does not understand table ownership, who placed the item, or semantic seat context. | Train/evaluate scene-specific ownership and table/seat context with consented site data. | "It can flag a supported unattended object, but it cannot determine whose table or seat it belongs to." |
| Pick-up, set-down, or push-in event recognition | Future deployment | No temporal action classifier or event-state model is called by the current application. | Frame/object detection does not prove these actions occurred. | Add labelled video sequences, temporal tracking/action recognition, validation, and event-specific UX. | "These actions are roadmap items, not current detections." |
| Suspicious item or bomb detection | Future deployment | Generic object detection and unattended timing only. | A generic model cannot identify or certify an explosive and must not create false safety assurance. | Safety-led threat-response design, specialist sensors/models, authority input, and formal validation. | "The system can report an unattended object; it does not determine that an object is a bomb." |
| Restricted/empty-zone motion at night | Future deployment | Zone CRUD and `unauthorized_access` detection type provide configuration foundations. | No schedule/after-hours rule or night calendar is implemented. | Add schedules/time zones, authorised occupancy rules, low-light validation, and escalation policy. | "Zones are configurable, but scheduled after-hours motion rules are future work." |
| Cats, dogs, or other animals | Future deployment | The packaged YOLO model may have generic COCO labels, but the deployed workflow/tests do not verify animal alert support. | No configured, validated animal-detection requirement or acceptance set. | Confirm classes, train if needed, and test on site-specific footage. | "Animal alerts are not a verified current feature." |
| Rat/pest detection | Future deployment | No verified rat-specific weights, detector, or rat test set exists. | Generic object detection cannot be presented as a reliable rat detector. | Acquire a pest dataset, train/tune a detector, test low-light/occlusion cases, and define response procedures. | "Rat detection is planned and is not enabled in this PoC." |
| Rat image, timestamp, and location | Partially supported | DetectionAlert can store snapshot metadata, `occurred_at`, zone/camera, and device source. SecurePi can save local snapshots. | These fields are generic alert infrastructure and are not rat records without a reliable rat detector; no general cloud image store exists. | Connect validated pest detection to controlled evidence storage and retention policy. | "The data model can carry time/location/snapshot metadata, but there is no rat detector producing those records." |
| Unique rat re-identification | Future research | No pest identity embedding, tracker, dataset, or evaluation exists. | Individual rat re-identification is materially harder than class detection and is unverified. | Dedicated dataset, tracking/re-identification model, reliability study, and privacy/operational review. | "Identifying the same rat again is research work, not a current capability." |
| Areas/shops frequented by pests | Future deployment | Zone/location and alert timestamps could support aggregation after reliable pest detection. | Analytics would be misleading without trustworthy pest observations and stable location history. | Add validated pest records, spatial/time aggregation, minimum-sample rules, and trend dashboard. | "Hotspot analytics depends on validated pest detections that do not yet exist." |
| Recognise the same known person again | Partially supported | Enrolled facial identity is recognised at Gate Scanner/V-Patrol checkpoints; Node confirms current user status in PostgreSQL. | This is checkpoint recognition, not passive continuous tracking; liveness is a PoC head-turn check. | Improve consent, calibration, evaluation, and checkpoint coverage if approved. | "An enrolled person can be recognised again at a scan point." |
| Continuous cross-camera person re-identification | Future deployment | No multi-camera identity graph, track hand-off, or cross-camera re-identification model exists. | Checkpoint facial recognition must not be equated with continuous person tracking. | Privacy impact assessment, camera calibration, tracking/re-ID model, retention controls, and extensive validation. | "Continuous cross-camera re-identification is not implemented." |

## Scope statement

The current submission is an academic proof of concept. Advanced pest analytics, temporal object-action recognition, threat classification and continuous multi-camera re-identification are documented as post-PoC deployment work and are not presented as completed features.
